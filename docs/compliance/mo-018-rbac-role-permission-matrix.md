## 1. Roles in MoDocument

A user holds **exactly one** role: a single enum column on `AppUsers`, asserted by `SodPolicyTest` (`src/test/java/com/modocument/application/security/SodPolicyTest.java`). Changing a role replaces it, and the change itself needs a second person's approval (`docs/security/maker-checker.md`).

| Code role | Who holds it | Where it can exist | Permissions (of 41) | MFA | Assignment rule |
|---|---|---|---|---|---|
| `READ_ONLY` | Bank auditors, controllers, second-line risk | Customer banks | 9 | Bank setting `security.mfa.requireForAllRoles` (default off) | `RoleAssignmentPolicy` (`src/main/java/com/modocument/application/security/RoleAssignmentPolicy.java`) |
| `READ_WRITE` | Bank operations staff and report authors: the makers | Customer banks | 21 | As above | As above |
| `APPROVER` | Bank supervisors: four-eyes checkers | Customer banks | 12 | As above | As above |

Two more rules apply on top of the matrix, both in `PermissionChecker.java`:

- A platform permission, or any permission held through `PLATFORM_ADMIN`, works only when the caller's bank is the platform bank.
- An `API_CLIENT` gets the intersection of the role's grants and its own scopes.

A user with a temporary password gets only `profile:self` until the password is changed.

## 5. Personal data access (for the DPO, MO-056)

Masking rules: `docs/security/masking-matrix.md` (`MaskingPolicy`, pinned by `MaskingMatrixDocTest`). Screen channel by role: `MaskingPolicy.screenChannel` (`src/main/java/com/modocument/application/privacy/MaskingPolicy.java`). Each row was observed in the live probe with synthetic values (`docs/compliance/evidence/A4-rbac-probe.md`, "Personal data" scenarios).

| Role | Sees unmasked client personal data? | Can export client data? | Notes |
|---|---|---|---|
| `READ_ONLY` | **No.** Job screens and records are masked (SCREEN_READONLY) | No (`export:run` not granted) | Sees bank-shared templates and their records, masked |
| `READ_WRITE` | **Yes**, on the working screens (SCREEN_WORKING): its own jobs, and the records of every **bank-shared** template, including colleagues' validated rows | Yes. Files and database exports are **masked for every role** (EXPORT) | Generated documents mask NIC, account and e-mail shapes (REPORT) |
| `APPROVER` | **Yes** on SCREEN_WORKING: bank-shared template records; the release queue shows the submitted documents' content | No | Holds no write permission |
| `ADMIN` | **Yes**: as READ_WRITE, plus data-subject search and export (DSR), which is raw by design (`src/main/java/com/modocument/api/controller/DataSubjectController.java`) | Yes, masked. DSR export is raw and audited (`DSR_EXPORTED`, `privileged-change` alert) | Can enable an outbound integration flow with masking off, but only with a second admin's approval (`INTEGRATION_FLOW_ENABLE`) |
| `PLATFORM_ADMIN` | **No** client data: no domain permission; cross-bank views are counts only | No | Can create a break-glass ADMIN in a customer bank (`BANK_ADMIN_ADD`, dual control). That is the one path from MO Intelligence staff to client data (`docs/compliance/policies/privileged-access-and-break-glass.md`) |
| `API_CLIENT` | Sends data in; reads results masked (EXPORT channel) | Results only, masked | Bound to its own bank |

Staff personal data (names and e-mails of bank users) is visible to holders of `user:admin` (user list and CSV export), `audit:read` and `siem:read` (audit trail).

**Points for the DPO's decision:**

1. Working-screen raw display (SCREEN_WORKING) now covers the records of bank-shared templates. So ADMIN, APPROVER and READ_WRITE colleagues see each other's raw validated rows. The existing justification in `docs/security/masking-matrix.md` ("jobs are strictly owner-scoped") predates the records feature. A bank can force masking with the setting `privacy.masking.screenWorking`. Exception X-03 in MO-019.
2. DSR export is raw and needs one ADMIN only: it is not maker/checker.
3. `BANK_ADMIN_ADD` break-glass, described above.

## 6. Least privilege: notes

| Principle | How the code applies it | Proof |
|---|---|---|
| Deny by default | Every route needs exactly one permission or sits on a 7-route public allowlist (login, refresh, MFA verify, SSO providers, synthetic probe, OAuth token, agent enrolment). An unknown or missing role gets 403 | `src/test/java/com/modocument/api/security/RoutePermissionCoverageTest.java`; `PermissionChecker.java` |
| Lowest role first | The JML runbook says to start at `READ_ONLY`. OIDC users get the provider's configured `default-role` | `docs/security/jml-runbook.md`; `docs/security/identity-providers.md` |
| Read ≠ export ≠ modify | Separate permissions: `READ_ONLY` cannot export, upload or use AI | Matrix §3; `RolePermissionMatrixTest.roleSemanticsHold` |
| Owner scoping inside a bank | Even an ADMIN cannot open another user's private template, job or document (404) | `TemplateOwnership.java`, `IngestionJobUseCase.java` (owner queries); probe "Owner scoping" |
| Platform staff hold no client data | `PLATFORM_ADMIN` has no domain permission; `lookup:admin` moved to the platform because the lookup tables are shared | `RolePermissions.java`; probe |
| Machine identities narrowed | API client = role grants ∩ client scopes ∩ expiry ∩ allowed CIDRs | `PermissionChecker.java`; `docs/security/maker-checker.md` (`API_CLIENT_CREATE`) |
| Database least privilege | The application connects as `modocument_app`: DML only, `NOBYPASSRLS`, owns nothing | `src/main/resources/db/migration/V12__app_role_grants.sql` |

**Gaps** (tracked in MO-019 §8 and the SEC-013 / SEC-017 pages):

- No time-bound elevation: a role is held until it is changed.
- `ADMIN` combines user administration with full data rights. There is no "user admin without data" role.
- `APPROVER` does not have to use MFA unless the bank enables it for all roles.

## 7. Separation of duties

The conflict table is data in `SodPolicy` (`src/main/java/com/modocument/application/security/SodPolicy.java`). It is described in prose in `docs/security/role-catalogue-and-sod.md`. Because a user holds one role, no toxic pair of roles can exist. The conflicts are operation-level:

| Operation | Duty A | Duty B | Refusal |
|---|---|---|---|
| `CHANGE_APPROVAL` (users, roles, password and MFA resets, templates, security settings, integrations, bank lifecycle) | Maker | Checker | 409 `SELF_APPROVAL_BLOCKED` |
| `DOC_RELEASE` | Author or submitter | Releaser | 409 `DOC_SELF_RELEASE_BLOCKED` |

A nightly scan (`src/main/java/com/modocument/infrastructure/sod/SodScanJob.java`) re-checks both invariants over stored data.

## 9. Keeping the matrix current

- **A change to the grants** is a code change to `RolePermissions.java`. The build fails until `docs/security/role-permission-matrix.csv` is regenerated, so every change appears as a reviewed diff (branch protection: `docs/security/branch-protection.md`).
- **A new route without a permission** fails `RoutePermissionCoverageTest`.
- **Who holds which role** is the only state that can drift. It is reviewed quarterly with the access-review worksheet (`docs/security/jml-runbook.md`).
- **Review cadence:** quarterly, together with the access review. Reviewers: Rushal (security) and the DPO (personal data). Sign-off: `TO CONFIRM (organisational)`.
