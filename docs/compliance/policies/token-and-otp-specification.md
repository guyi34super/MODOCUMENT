# Token, OTP and credential specification

Controls: **SEC-022** (time-based passwords and one-time codes) and **SUP-S02** (token architecture).
Gate items B3, B4 and B5. Written from the code on 2026-10-19. Every value below is the shipped
default; where a bank or the platform owner can change it, the allowed range is given and the
setting is named.

**Not present in MoDocument:** e-mail or SMS one-time codes and self-service password-reset
links. A forgotten password is reset only by an administrator under maker/checker
(`POST /api/admin/users/{id}/password-reset`, `src/main/java/com/modocument/api/controller/UserAdminController.java`).
OIDC sign-in (Entra ID, Keycloak) uses Spring Security's authorization-code flow with its
built-in `state` handling; the identity provider's own reset links and OTP lifetimes are set in
the provider and are `TO CONFIRM (organisational)` per bank.

## 2. Token architecture (SUP-S02)

* **Signing.** User and client tokens are HS256-signed with one key, `MODOCUMENT_JWT_SECRET`
  (at least 32 bytes, the old development key is refused outside dev). The decoder pins
  `MacAlgorithm.HS256`, so `alg=none` or any other algorithm fails
  (`src/main/java/com/modocument/api/config/SecurityConfig.java`).
* **Validation order** on every request: signature, `exp`/`nbf` (`JwtTimestampValidator`),
  revocation (`RevocationValidator`), then the MFA-challenge scope check.
* **Revocation.** Logout puts the access token's `jti` in `RevokedToken` and revokes all the
  user's refresh tokens. Password change, an approved admin password reset, role change, disable,
  MFA reset, an IdP role change at OIDC sign-in and bank suspension bump `AppUsers.TokenVersion`
  (`src/main/java/com/modocument/application/usecase/UserAdminUseCase.java`,
  `src/main/java/com/modocument/infrastructure/security/oidc/OidcLoginService.java`,
  `src/main/java/com/modocument/application/usecase/PlatformBankLifecycleUseCase.java`); a token
  whose `token_ver` is older is refused on the next request. One indexed database read per
  request, no cache.
* **Refresh rotation and reuse detection.** Each refresh returns a new token in the same family
  and stamps the old one `RevokedAt`/`ReplacedByJti`. A second use of an old token revokes the
  family. Clean-up: `HousekeepingJob` deletes refresh tokens 30 days after expiry or revocation
  and denylist rows after the token's own expiry
  (`src/main/java/com/modocument/infrastructure/housekeeping/HousekeepingPurger.java`).
* **Bridge for SSO.** An Entra ID or Keycloak token is never accepted by the API. After the
  OIDC handshake MoDocument issues its own pair (`docs/security/identity-providers.md`).
* **Machine clients** never mix with users: `/api/integration/v1/**` and `/api/agent/v1/**`
  admit only `ROLE_API_CLIENT`; every other route refuses it.

## 3. Differences from the workbook design

| Workbook design (SUP-S02, SEC-022) | MoDocument today | Position |
|---|---|---|
| RS256/EdDSA keys in the vault with `kid`-based rotation | One HS256 key; rotation means a new value and a rolling restart, which ends all sessions (register K1, 180 days) | Gap (Build, low urgency): no overlap window and the signing key is shared by user and client tokens |
| Validate `iss` and `aud` strictly | Tokens carry no `iss` or `aud`; only `exp`/`nbf` and the revocation checks | Gap (Build): add `iss`/`aud` claims and validators |
| Refresh tokens bound to the client | Bound to the browser by the path-scoped, `SameSite=Strict`, `HttpOnly` cookie; IP and user agent are recorded, not enforced | Accepted design |
| Email/SMS OTP 6–8 digits, 5–10 min, 3 attempts | Not used | Not applicable |
| Reset links expire | No reset links; temporary passwords have **no expiry** | Gap (Build): expire an unused temporary password (for example 72 h) |
