## Requirement
Prove that plaintext passwords never persist or travel unprotected, including in logs and crash
dumps. Gate B2 acceptance: a search of 30 days of aggregated logs for seeded canary passwords
returns nothing.

## How MoDocument meets it today
- **At rest:** passwords are kept only as Argon2id hashes; temporary passwords are hashed at
  submit so the maker/checker queue never holds plaintext
  (`src/main/java/com/modocument/api/config/SecurityConfig.java`,
  `src/main/resources/db/migration/V80__ws10_pending_change.sql`). Details:
  [credential-storage-and-reset-design.md](../policies/credential-storage-and-reset-design.md).
- **In responses:** no API returns a password or hash
  (`src/main/java/com/modocument/application/dto/UserDto.java`). Password-policy error messages
  never echo the password (`src/main/java/com/modocument/application/security/PasswordPolicy.java`).
- **In logs (scrubbing configuration):** every console line goes through `%mask` and every stack
  trace through `%maskEx` (`src/main/resources/logback-spring.xml`,
  `src/main/java/com/modocument/infrastructure/logging/RedactingConverter.java`,
  `src/main/java/com/modocument/infrastructure/logging/RedactingThrowableConverter.java`); the
  structured JSON profile uses `RedactingJsonMembersCustomizer`. All three use one pattern set
  (`src/main/java/com/modocument/application/privacy/PiiPatterns.java`): `password`, `secret`,
  `token`, `api_key`, `client_secret`, `authorization`, `credential` and the refresh cookie
  values, `Bearer` tokens, JWT-shaped strings, e-mails, NIC and account numbers.
- **No request-body logging and no external error tracker** are configured (no Sentry or similar
  dependency in `pom.xml` or `frontend/package.json`).
- **In transit:** TLS 1.2+ at CloudFront and the ALB (`infra/terraform/modules/edge/main.tf`,
  `infra/terraform/modules/ecs-app/main.tf`); HSTS on the SPA and API.
- **Identity providers:** Keycloak and Entra ID hash their own passwords; MoDocument never sees
  an SSO user's password (`docs/security/identity-providers.md`).

## Questionnaire answer (final)
No. MoDocument never stores or logs a password in plain text. Passwords are kept only as salted
Argon2id hashes, are sent only over TLS, and are never returned by any screen or API. All
application log output, including error stack traces, passes through a redaction layer that masks
password, secret and token values; an automated test sends a sign-in with a seeded canary password
and fails the build if the canary appears anywhere in the log output. For users who sign in
through Microsoft Entra ID or Keycloak, MoDocument never receives the password at all. Evidence:
SEC-019-E01.

## Test SEC-019-T01
- **Procedure:** run `LogRedactionCanaryTest` (a failed `POST /api/auth/login` carrying a canary
  password and e-mail, exception logs with NIC/account/e-mail, a `password=` / `Bearer` / refresh
  cookie / JWT log line; then every captured log event is rendered through the production layout
  and the real console output is searched), `RedactingConverterTest` and
  `StructuredLogRedactionTest`.
- **Expected:** no canary in any log output; the mask marker present.
- **Actual (2026-10-19):** LogRedactionCanaryTest 1/1, RedactingConverterTest 15/15,
  StructuredLogRedactionTest 2/2 — all pass (batch 1).
- **Result:** Pass for the application; the live 30-day log search is not possible before
  deployment.
- **Tester:** Agent A6 (automated re-performance); human sign-off required. **Date:** 2026-10-19.

## Risk R-SEC-019
Log aggregation becomes a password database. Cause in the workbook: the request logger captures
login payloads. MoDocument has no payload logger and masks credential fields in every log path;
the remaining exposure is outside the application (edge logs). Likelihood, impact and residual are
set in MO-031.
