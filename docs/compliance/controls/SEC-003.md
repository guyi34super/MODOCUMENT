## Requirement

Automate horizontal scaling on real signals; use vertical scaling as a planned capacity change.
Acceptance (gate A10): scale-out observed automatically under synthetic load with zero 5xx
during the event.

## How MoDocument meets it today

**Horizontal (designed in Terraform, not applied).**

| Setting | Value | Proof |

**Vertical (planned change through Terraform).** Task size is `task_cpu` / `task_memory`
(1,024 units / 3,072 MiB; app container 896 units / 2,816 MiB), node type `instance_type`, and
the RDS class `db_instance_class` (`db.m6g.large` production, `db.t4g.medium` staging): each is
a Terraform variable changed through the release process, with validation on allowed task sizes
(`infra/terraform/modules/ecs-app/variables.tf`, `infra/terraform/envs/production/variables.tf`,
`docs/release/runbook.md`). The JVM sizes its heap from the container limit
(`-XX:MaxRAMPercentage=70`, `docker-entrypoint.sh`), so a larger task gets a larger heap without
a code change.

**What the application needs to scale horizontally.** Stateless JWT sessions and S3 file storage
(`infra/terraform/modules/ecs-app/main.tf`, `file_store`) allow more tasks. Two parts are per
instance: rate-limit counters (N tasks allow N × each limit, `docs/security/owasp-api-top10.md`
API4) and the in-memory ingestion queue (`src/main/java/com/modocument/infrastructure/ingestion/IngestionJobRunner.java`).

**What the test box shows about the vertical limit** (MO-017 §5, one CPU ≈ one task):

| Load | One CPU (pinned) | 4 shared CPUs |
|---|---|---|
| 1× assumed peak (50 users) | 0 errors, p95 read 56 ms; JVM CPU 53 % mean | 0 errors, p95 read 13 ms; JVM CPU 36 % |
| 2× assumed peak (100 users) | 0 errors, p95 read 93 ms; JVM CPU **73 %** mean | 0 errors, p95 read 21 ms; JVM CPU 81 % |
| Breakpoint capacity within thresholds | 100 fast users ≈ **236 req/s** | 300 fast users ≈ **715 req/s** |
| Latency breaking point | 150 users | 400 users |
| Generation saturation | 15–17 flows/s | not reached at 40 users (24 flows/s) |

So the scaling signal is right for this workload: CPU is the resource that saturates first
(the pinned JVM reached 90–94 % of its core while the pool never timed out and no request
failed), and one task crosses the 60 % CPU target between 1×
and 2× of the assumed peak, which is where target tracking should add a task. Adding cores raised
throughput about 3× (236 → 715 req/s) on a shared box. Arithmetic, not measured: 8 tasks at the
one-CPU figure would be about 1,900 req/s if the database keeps up; 8 × 20 pool connections =
160, which has to stay under the RDS `max_connections` (formula in
`src/main/resources/application.yml`, Hikari comment).

## Questionnaire answer (final)

MoDocument is designed to scale horizontally and automatically: the ECS service uses
target-tracking autoscaling on average CPU (target 60 %), with a minimum of 2 tasks across two
availability zones and a hard maximum of 8 tasks, and the EC2 capacity behind it scales from 2
to 4 instances through an ECS capacity provider. Vertical scaling (task CPU and memory, node
type, database class) is a planned change made through Terraform under the release process; the
JVM heap follows the container size automatically. A stress test on 19 October 2026 confirmed
that CPU is the resource that saturates first and that one production-sized instance handles
twice the assumed peak (100 concurrent users) without errors at about 73 % CPU, so the CPU signal
triggers scale-out before users are affected. The environment is pre-production: the scaling
configuration is in code but not yet deployed, and the scale-out event under load will be
observed and recorded on the staging environment before go-live. Evidence: SEC-003-E01.

## Test SEC-003-T01

**Procedure.** (1) Inspect the Terraform for target tracking, min ≥ 2 across zones, a hard max
and cooldowns. (2) On the test box, measure the vertical limit of one instance with one CPU and
with 4 CPUs (MO-016 S4-lite and S6). (3) On staging: drive load past the target and record the
scale-out event and 5xx count (not possible yet).

**Expected result.** Scale-out observed automatically under synthetic load with zero 5xx during
the event.

**Actual result (2026-10-19).** (1) Present: CPU target 60 %, min 2, max 8, cooldowns 60/300 s,
ASG 2–4 nodes with managed scaling and a placeability precondition. (2) One CPU: 0 errors at 1×
and 2× of the assumed peak (JVM CPU 53 % / 73 % mean); 236 req/s within thresholds; latency
break at 150 fast users; 0 errors at every step up to 300 users. 4 CPUs: 715 req/s within
thresholds, break at 400 users, 0 errors. (3) Not run: nothing is deployed.

**Result: Partial.** Tester: Agent A3 (automated re-performance); human sign-off required.
Date: 2026-10-19.

## Risk R-SEC-003

Saturation during peaks, or over-provisioning cost the rest of the time. Cause: autoscaling
configured but never observed working. Mitigation: CPU-based target tracking with a hard cap
(designed), measured per-instance limits (MO-017), the CPU alarm at the cap, and the staging
scale-out test. Likelihood, impact and residual are set in MO-031.
