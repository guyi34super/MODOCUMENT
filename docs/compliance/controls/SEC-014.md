## Requirement
Provide native MFA and enterprise SSO, enforceable per role. Gate B2/B3 acceptance: an admin
account cannot complete sign-in or step-up actions without the second factor.

## How MoDocument meets it today
- **Native TOTP MFA** (RFC 6238) with QR enrolment, 10 hashed recovery codes, replay protection
  and per-user rate limiting (`src/main/java/com/modocument/application/usecase/MfaUseCase.java`,
  `src/main/java/com/modocument/infrastructure/security/totp/Totp.java`). Sign-in is two-phase: a
  correct password returns only a 5-minute challenge; no token is issued before the code verifies
  (`src/main/java/com/modocument/application/usecase/AuthUseCase.java`).
- **Enforcement policy per role and bank** (`AuthUseCase.mustEnrolMfa`, settings in
  `src/main/java/com/modocument/infrastructure/settings/SettingDefinitions.java`): see the matrix.
- **Enterprise SSO (OIDC)**: Microsoft Entra ID and Keycloak, optional, configured per provider
  (`application-oidc.yml.example`, `src/main/java/com/modocument/infrastructure/security/oidc/OidcLoginService.java`).
  The Keycloak realm in the repository forces TOTP enrolment for every user
  (`docker/keycloak/modocument-realm.json`, `CONFIGURE_TOTP` default required action, checked by
  `KeycloakRealmConfigTest`). Entra ID MFA is a Conditional Access policy in the bank's tenant.
- **MFA administration**: an administrator can remove another user's MFA enrolment only under
  maker/checker (`USER_MFA_RESET`), which also ends that user's sessions
  (`src/main/java/com/modocument/api/controller/UserAdminController.java`).

### MFA enforcement matrix

| Role | Local password sign-in | OIDC sign-in (Entra ID / Keycloak) |
|---|---|---|
| `PLATFORM_ADMIN` | TOTP always required; no setting can turn it off | Refused: platform accounts never get an OIDC session |
| `ADMIN` | TOTP required: bank setting `security.mfa.requireForAdmins` is locked to `true` (yml `modocument.security.mfa.require-for-admin`, default `true`) | Enforced by the IdP only (Keycloak realm OTP; Entra Conditional Access); MoDocument does not check the token's `amr`/`acr` |
| `APPROVER`, `READ_WRITE`, `READ_ONLY` | Required when the bank turns on `security.mfa.requireForAllRoles` (default `false`); otherwise optional self-enrolment on the profile page | Enforced by the IdP only |
| `API_CLIENT` (machine) | Not applicable: OAuth2 client credentials, API key or mutual TLS; IP allow-list optional | Not applicable |

### SSO configuration sample
- Keycloak realm: `docker/keycloak/modocument-realm.json` (password policy, TOTP policy 6 digits /
  30 s, `CONFIGURE_TOTP` default, confidential client `modocument-app`, role claim
  `modocument_roles`).
- Entra ID and Keycloak provider entries: `application-oidc.yml.example`; set-up steps and the
  B2/B3 evidence checklist: `docs/security/identity-providers.md`.

## Questionnaire answer (final)
Yes. MoDocument has built-in multi-factor authentication with authenticator-app one-time codes
(TOTP) and one-time recovery codes. A second factor is mandatory for bank administrators and for
the platform owner's accounts, and each bank can make it mandatory for all its users; a password
alone never produces a session for these accounts. MoDocument also supports single sign-on through
OpenID Connect with Microsoft Entra ID and Keycloak. On that path the identity provider enforces
MFA: through the bank's Entra Conditional Access policy, or through the Keycloak realm, which
requires every user to enrol an authenticator. Evidence: SEC-014-E01.

## Risk R-SEC-014
One phished password equals full admin takeover. Cause in the workbook: MFA optional and not
enforced for admins. For local sign-in this cause is closed; it remains possible through a
misconfigured IdP or a compose deployment that keeps the `false` default. Likelihood, impact and
residual are set in MO-031.
