## Requirement
Dual control on every critical change: one identity proposes it and a different identity approves it. An attempt by the maker to be the checker must return a hard error and be logged.

## How MoDocument meets it today
The workbook says "not implemented; one person makes user, role and template changes alone". The repository now has a complete pending-change workflow (`docs/security/maker-checker.md`).

- **Critical-change list.** There are 17 change types (`src/main/java/com/modocument/application/security/ChangeAudience.java`):
  - Users: `USER_CREATE`, `USER_ROLE_CHANGE`, `USER_DISABLE`, `USER_PASSWORD_RESET`, `USER_MFA_RESET`.
  - Templates: `TEMPLATE_UPDATE`, `TEMPLATE_DELETE`.
  - Bank security settings: `SETTING_UPDATE`.
  - Integrations: `INTEGRATION_CONNECTION_CHANGE`, `INTEGRATION_FLOW_ENABLE`, `API_CLIENT_CREATE`, `AGENT_REGISTER`.
  - Platform: `PLATFORM_SETTING_UPDATE`, `BANK_CREATE`, `BANK_SUSPEND`, `BANK_ADMIN_ADD`, `EGRESS_RULE_APPROVE`.

  Changes to the role–permission matrix itself are code changes. They go through pull-request review (`docs/security/branch-protection.md`).
- **Pending until approved.**
  - The maker's request is stored as a `PendingChange` (status `REQUESTED`) and nothing happens.
  - A different user holding `change:approve` in the right audience applies it in the same transaction as the approval, re-checking every rule at that point (`src/main/java/com/modocument/application/usecase/PendingChangeUseCase.java`).
  - Platform changes need a second **platform** admin.
- **Self-approval hard-blocked, even for administrators.**
  - `SodPolicy.verifyDistinct` refuses with 409 and writes a `SELF_APPROVAL_BLOCKED` audit row with outcome DENIED, in its own transaction so that the row survives the refusal (`src/main/java/com/modocument/application/security/SodPolicy.java`).
  - There is no switch for the user-security types.
  - The template types can be switched off only for a single-user development setup (`modocument.security.maker-checker.template-changes`).
- **Every bank needs at least two approvers.**
  - `BANK_CREATE` requires at least one ADMIN and at least two ADMIN/APPROVER users (`docs/platform/platform-owner.md`).
  - Platform admins never drop below two.
  - A fresh install can seed a second bootstrap ADMIN (`MODOCUMENT_BOOTSTRAP_SECOND_ADMIN_EMAIL`), and it warns at every start when the default bank has fewer than two.
- **Deliberately direct:** the lower-risk directions. Re-enabling a user, unlocking, renaming, revoking or rotating an API client, revoking an agent, reactivating a bank, and disabling or creating (disabled) integration flows (`docs/security/maker-checker.md`).

## Questionnaire answer (final)
Critical changes in MoDocument always need two different people:

- user creation, role changes, account disabling, password and MFA resets;
- template changes and deletions;
- security settings;
- integration connections, outbound data flows, API clients and connector agents;
- every platform-level change, such as onboarding or suspending a bank.

The change is held as pending, with no effect, until a different authorised user approves it. If the requester tries to approve their own change, the system returns an error and records the attempt in the audit trail. This applies to administrators too. Every bank is created with at least two administrators or approvers, so a second approver is always available. We verified this on a running system. Evidence SEC-023-E01.

## Test SEC-023-T01
- **Procedure:**
  1. Run `MakerCheckerIntegrationTest` and `PendingChangeAudienceTest`.
  2. On the live stack, an ADMIN submits a role change and then approves it themselves. A different user then decides it.
  3. Platform admin 1 submits `BANK_CREATE` and approves it themselves. Platform admin 2 then approves it.
- **Expected result:** a maker = checker attempt returns a hard error in the test, and the attempt is logged.
- **Actual result:**
  - The tests passed: 6 and 40 (`docs/compliance/evidence/A4-test-runs.md`).
  - Live: the role change returned 202 while pending, the self-approval returned 409, and the APPROVER's rejection returned 200.
  - The platform self-approval returned 409, and the second platform admin's approval created the bank.
  - The `SELF_APPROVAL_BLOCKED` DENIED audit row is asserted in `MakerCheckerIntegrationTest`.
- **Result:** Pass · tester: Agent A4 (automated re-performance); human sign-off required · date: 2026-10-19

## Risk R-SEC-023
- **Risk:** one compromised or malicious user changes limits or configuration alone.
- **Cause:** an approval step exists, but the maker can approve their own change.
- **Mitigation:** self-approval is refused by `SodPolicy` for everyone, and refusals are audited. The nightly `SodScanJob` re-checks that no applied change has maker = checker.

Likelihood, impact and residual are set in MO-031.
