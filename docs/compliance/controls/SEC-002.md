# SEC-002 — How the solution handles peak load and performance degradation

## Requirement

Engineer graceful behaviour under overload: scale, shed, queue — never collapse. Acceptance: at
2× expected peak the error budget holds and no cascading failure occurs in test (gate items
A10, A12, E7).

## How MoDocument meets it today

| Mechanism | What it does | Proof |
|---|---|---|
| Per-user API rate limits | One interceptor meters every expensive route per user (uploads 20/h, ingestion 60/h, exports 60/h, document generation 30/h, extraction 30/h, DSR 10/h, …) and answers **429 with `Retry-After`** | `src/main/java/com/modocument/infrastructure/ratelimit/ApiRateLimitInterceptor.java`, `src/main/java/com/modocument/infrastructure/ratelimit/ApiRateLimitProperties.java`, `src/main/resources/application.yml` (`modocument.ratelimit`), `docs/security/owasp-api-top10.md` (bucket table), `ApiRateLimitIntegrationTest` |
| Editable limits | Each bucket is a bank setting with hard limits (e.g. `ratelimit.docGenerate` 1–300) | `docs/settings/catalogue.md` |
| Sign-in throttles | Per IP and per e-mail windows before any password hashing | `src/main/java/com/modocument/infrastructure/ratelimit/AuthRateLimiter.java` |
| LLM quota | 60 model calls per user per hour | `src/main/java/com/modocument/infrastructure/ratelimit/LlmRateLimiter.java` |
| AI circuit breaker | Opens after 5 consecutive failures for 2 minutes; ingestion completes by code (`CIRCUIT_OPEN`); a trial call closes it; opening is audited and alerted (`ai-circuit-opened`, HIGH) | `src/main/java/com/modocument/infrastructure/ai/AiCircuitBreaker.java`, `src/main/resources/application.yml`, `AiCircuitBreakerTest` |
| Bounded resources | DB pool max 20 per instance with a 10 s wait; ingestion stages on 2 background threads | `src/main/resources/application.yml`, `src/main/java/com/modocument/infrastructure/ingestion/IngestionJobRunner.java` |
| Edge rate rules (design) | WAF per-IP cap 2,000 per 5 minutes; `/api/auth/*` 100 per 5 minutes | `infra/terraform/modules/edge/main.tf`, `infra/terraform/modules/edge/variables.tf` |
| Autoscaling (design) | ECS target tracking at 60 % CPU, 2–8 tasks hard cap (see [SEC-003](SEC-003.md)) | `infra/terraform/modules/ecs-app/main.tf` |
| Alarms (design) | ALB 5xx burst and sustained CPU at the cap → SNS | `infra/terraform/modules/security-monitoring/main.tf` |
| Degradation runbook | Levels L0–L4, signals, operator actions, recovery check, known limits | [policies/degradation-runbook.md](../policies/degradation-runbook.md) |
| Measured behaviour | Stress test of 2026-10-19 on the test box | [MO-017](../mo-017-stress-testing-report.md), `perf/results/stress-2026-10/main/s4.summary.json` |

What is **not** built: report generation is synchronous (no queue, the workbook's "queue
report generation under load"); rate-limit counters are in memory per instance; the WAF, scaling
and alarms are Terraform not yet applied (`NOT IN REPO (live cloud)`).

## Questionnaire answer (final)

MoDocument protects itself from overload at three layers. At the edge, the design puts a WAF
per-IP rate rule in front of the application (CloudFront + AWS WAF, Terraform). In the
application, every expensive operation (uploads, ingestion runs, exports, document generation,
extraction, AI calls, sign-in) has a per-user or per-IP limit that answers HTTP 429 with a
`Retry-After` header, so one user or script cannot exhaust the service; an AI circuit breaker
stops calling a failing model after 5 consecutive failures and the ingestion pipeline completes
jobs with its code extractor instead. The service runs on ECS with CPU-based autoscaling between
2 and 8 tasks (hard cap). A stress test on 19 October 2026 (synthetic data, one application
instance on a shared 4-vCPU test machine) ran a realistic user mix at 1×, 2× and 4× an assumed
peak of 50 concurrent users with 0 errors in 26,438 requests across the S4 stages (26,439 including one request between stages), p95 latency under 50 ms for reads
at 2× peak, and full recovery after the spike; every rate limit returned 429 with `Retry-After`
exactly at its limit while other users were unaffected. Production-environment confirmation
(staging load test, applied WAF and scaling) is scheduled before go-live. Evidence: SEC-002-E01.

## Test SEC-002-T01

**Procedure.** Re-perform the acceptance test on the test box (`e2e/run-local.sh`, one
instance, rate limits raised for capacity, default limits for the 429 check): S4 peak mix
at 25 → 50 (1×) → 100 (2×) → 200 (spike) → 25 VUs; S5a default-limit probes; S5b AI failure; S5c
pool pressure; S6 breakpoint with recovery. Commands in
[evidence/A3-stress-runs.md](../evidence/A3-stress-runs.md).

**Expected result.** At 2× expected peak the error budget (< 1 %) holds and no cascading failure
occurs; overload controls shed or queue.

**Actual result (2026-10-19).**

| Check | Result |
|---|---|
| 2× peak (100 VUs, 180 s) | 11,103 requests, **0 errors**, 61.7 req/s; p95 read 21.3 ms, write 51.7 ms, heavy 66.7 ms, sign-in 92.4 ms; probe 90/90 |
| Spike 200 VUs (60 s) then 25 VUs | 7,552 requests, 0 errors; recovery stage p95 read 12.7 ms (back to the 1× level) |
| Default limits | 429 exactly at the limit for `doc-generate` (31st call), `ingestion` (61st incl. seed), `exports` (61st), `uploads` (21st incl. seed), sign-in per e-mail (201st); `Retry-After` 3,585–3,598 s (870 s for sign-in); another user of the same bank still 200; a 429 costs 4–10 ms median |
| AI model failing | 20/20 jobs VALIDATED (6 by code with reason ERROR, then 14 with CIRCUIT_OPEN); model calls stopped after the breaker opened (0 calls in the next 5 jobs); after 2 minutes the model was used again (3/3 AI) |
| Pool pressure (200 VUs, no think time) | 26,210 requests, 0 errors; pool at its 20-connection maximum and Tomcat's 200 threads busy; latency rose (read p95 1,205 ms) instead of failing |
| Breakpoint | No errors up to 400 VUs (744 req/s); throughput plateau from 300 VUs with the machine's CPU at 97–99 %; recovery at 10 VUs: read p95 11.3 ms |

**Result: Partial** — the application-level acceptance passes on the test box; the
production-environment part (WAF, autoscaling, staging run at the real expected peak) is not
yet testable. Tester: Agent A3 (automated re-performance); human sign-off required. Date:
2026-10-19.

## Risk R-SEC-002

A traffic spike or an abusive client cascades into a full outage and an SLA breach. Cause: no
capacity figure for production, single-instance in-memory limits, synchronous heavy work.
Mitigation: per-user limits and the circuit breaker (tested), WAF and autoscaling (designed),
the degradation runbook, and the staging re-run. Likelihood, impact and residual are set in
MO-031.
