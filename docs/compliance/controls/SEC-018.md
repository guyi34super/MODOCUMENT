# SEC-018 — Credentials stored in a secure vault

| Workbook | Area | Priority | Status (repo-verified) | Evidence ID | Test ID | Risk ID |

## Requirement
No plaintext secret at rest anywhere: user passwords hashed, system secrets vaulted. Gate A7
acceptance: the repository history scan is clean, and revoking a vault lease demonstrably cuts an
application's database access.

## How MoDocument meets it today
- **User passwords — hashing configuration in code.** `DelegatingPasswordEncoder` with Argon2id
  for every new hash (`Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`: 16-byte salt per
  hash, 32-byte hash, parallelism 1, 16 MiB memory, 2 iterations); BCrypt only to match legacy
  hashes, which are re-hashed to Argon2id at the next sign-in and audited `PASSWORD_REHASHED`
  (`src/main/java/com/modocument/api/config/SecurityConfig.java`,
  `src/main/java/com/modocument/application/usecase/AuthUseCase.java`). MFA recovery codes and
  API client secrets use the same encoder.
- **System secrets — vault.** Production secrets are AWS Secrets Manager entries created as empty
  shells by Terraform and filled by the key owner (`MODOCUMENT_JWT_SECRET`, `MODOCUMENT_MFA_KEY`,
  `MODOCUMENT_CONNECTOR_KEY`, the runtime DB credentials, bootstrap admin secrets)
  (`infra/terraform/envs/production/main.tf`). The ECS task reads only those exact ARNs
  (`secretsmanager:GetSecretValue`, no wildcard) and injects them with `valueFrom`
  (`infra/terraform/modules/ecs-app/main.tf`). The RDS master password is RDS-managed
  (`manage_master_user_password = true`) and the database is encrypted with a KMS key that has
  rotation enabled (`infra/terraform/modules/rds/main.tf`).
- **No secrets in code or config.** The app refuses to start without `MODOCUMENT_JWT_SECRET` or
  with the old public development key; compose requires its secrets with `${VAR:?}`; every secret
  can also be read from a file (`<NAME>_FILE`, `src/main/java/com/modocument/infrastructure/security/SecretFileEnvironmentPostProcessor.java`)
  (`docs/security/web-hardening.md` §5c).
- **Application-level vaults.** TOTP secrets are AES-256-GCM encrypted
  (`src/main/java/com/modocument/infrastructure/security/MfaSecretCipher.java`); bank connection
  credentials are sealed per bank with a key version for rotation
  (`src/main/java/com/modocument/infrastructure/integration/secrets/ConnectorSecretVault.java`).
- **Rotation configuration.** Rotation cadences and owners are in the key register: JWT key and
  runtime DB password 180 days, MFA and connector keys annually, RDS master AWS-managed, KMS
  annual auto-rotation (`docs/security/key-certificate-register.md`).
- **Repository history scan.** gitleaks runs over the full history in CI
  (`.github/workflows/security.yml`). Run for this pack on 2026-10-19: 270 commits of `origin/main`,
  no leaks (`docs/compliance/evidence/A6-test-runs.md`).

## Questionnaire answer (final)
Yes. MoDocument keeps no plaintext credential at rest. User passwords for MoDocument's own sign-in
are stored only as salted Argon2id hashes; users who sign in through Microsoft Entra ID or Keycloak
have no MoDocument password. System credentials (token-signing key, encryption keys, database
credentials) are held in AWS Secrets Manager and injected into the running service at start-up;
they are never in source code, images or configuration files. Credentials for a bank's own systems
are encrypted with a per-bank key. A secret scan over the full repository history finds no secrets.
Evidence: SEC-018-E01.

## Risk R-SEC-018
A repository leak or a configuration read yields production credentials. Cause in the workbook:
secrets in environment files committed to the repository. The history scan is clean and the
deployment design keeps secrets in Secrets Manager. Likelihood, impact and residual are set in
MO-031.
