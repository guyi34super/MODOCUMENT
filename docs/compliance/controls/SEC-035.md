## Requirement
A tamper-evident, append-only audit trail capturing who, what, when and where, with before-and-after state. Acceptance (gate C7): manually editing an audit row in a test database is (a) blocked by grants, and (b) if forced as superuser, flagged by the next verification run.

**Tamper drill (2026-10-19, `docs/compliance/evidence/A7-audit-tamper-drill.md`):** on a fully migrated PostgreSQL database the runtime role holds `INSERT, SELECT` only and both triggers are enabled. A superuser who sets `session_replication_role = replica` updated an audit row (`PG_IT_PROBE` → `TAMPERED`, then rolled back). Nothing would detect such an edit.

Also noted: `ExtractionAuditEvent` (the extraction fetch log, `src/main/resources/db/migration/V11__bankid_tenant_columns.sql`) has no append-only grants or triggers.

## Questionnaire answer (final)
MoDocument writes an append-only audit trail for every security-relevant action: the individual user (or machine client), their role, bank, session and IP address, the request ID, the time, the action and the affected record with its old and new values, and the outcome. Successful changes are recorded in the same database transaction as the change itself, so no change can commit without its audit record. The application's database role can only insert and read audit records, and database triggers refuse any update, delete or truncate, even by the table owner; an automated test on PostgreSQL proves both. Administrators and approvers can search, compare and export the trail in an audit viewer, and that access is itself audited. Records are kept for seven years. A database superuser could still bypass the triggers; to make such tampering detectable we are adding a hash chain over the records with a daily verification job before go-live (evidence SEC-035-E01).

## Test SEC-035-T01
- **Procedure:** (1) Run `AuditAppendOnlyPgIT` on PostgreSQL (`mvn -Ppostgres-it -Dit.test=AuditAppendOnlyPgIT verify`, run R3). (2) Run the H2 audit tests `JpaAuditRecorderTest`, `AuditLogApiTest`, `AuditViewAuditQaTest`, `AuditTrailGapsTest`, `AuditActionCatalogueDocTest` (run R1). (3) Tamper drill as superuser (run R4).
- **Expected result:** (a) app role and owner cannot edit; (b) a forced superuser edit is flagged by the next verification run.
- **Actual result:** (1) 5 tests, 0 failures: app role inserts inside its tenant only, fails closed without a tenant, gets "permission denied" on UPDATE/DELETE/TRUNCATE; the owner is stopped by the trigger; RLS covers the table. (2) 33 tests, 0 failures. (3) Grants: `modocument_app` = INSERT, SELECT; triggers enabled; superuser update with `session_replication_role = replica` succeeded (rolled back); no verification exists to flag it.
- **Result:** Partial — (a) Pass, (b) Fail
- **Tester:** Agent A7 (automated re-performance); human sign-off required. **Date:** 2026-10-19

## Risk R-SEC-035
- **Risk:** a privileged insider edits history and nothing detects it.
- **Cause:** append-only enforcement relies on grants and triggers that a database superuser can bypass; no hash chain or verification job.
- **Mitigation:** hash chain with daily verification and external anchoring; restricted, logged superuser access; archive with Object Lock.
- Likelihood, impact and residual: set in MO-031.
