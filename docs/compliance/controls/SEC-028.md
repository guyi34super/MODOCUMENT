## Requirement
Encrypt every store and every hop, including the ones assessors check: backups, caches, internal traffic. Acceptance (gate C4): an SSL Labs A grade externally; the internal database connection shown as TLS in `pg_stat_ssl` or equivalent.

## How MoDocument meets it today

Encryption is designed into the application and the Terraform. The Terraform has **not been applied** (`infra/terraform/README.md`), so the cloud rows are configuration, not running systems. Algorithms and key sizes: `docs/security/crypto-standard.md`.

### SSL-enforcement configuration
- Server side: `rds.force_ssl = 1` in the RDS parameter group (`infra/terraform/modules/rds/main.tf`).
- Client side: `sslmode=verify-full&sslrootcert=/app/certs/rds-global-bundle.pem` in both environments' JDBC URL (`infra/terraform/envs/production/main.tf`, `infra/terraform/envs/staging/main.tf`); the app and Flyway share the URL; local default `prefer` (`src/main/resources/application.yml`, `docker-compose.yml`).

## Questionnaire answer (final)
All MoDocument data stores are encrypted at rest: the PostgreSQL database and its automated backups with a dedicated, yearly-rotated KMS key; the document file store (S3) with its own KMS key enforced by bucket policy; logs, secrets and server disks with AWS-managed keys. Credentials stored by the application are additionally encrypted field by field with AES-256-GCM (MFA seeds; bank connection secrets with a separate key per bank) or stored only as Argon2id/SHA-256 hashes. In transit, users and bank systems reach MoDocument over TLS 1.2 or 1.3 only (optionally with mutual TLS for bank systems); the application connects to the database over TLS that the server enforces and the client verifies against the AWS certificate authority; file transfers use HTTPS or SFTP with a pinned host key. MoDocument is pre-production and the infrastructure is defined as code but not yet deployed, so the external TLS grade and the live database TLS check will be produced at go-live. Two hardening items are planned before go-live: TLS between the load balancer and the application containers, and dedicated keys for the backup vaults and log archive (evidence SEC-028-E01).

## Risk R-SEC-028
- **Risk:** an unencrypted internal hop or a backup becomes the plaintext source of bank data.
- **Cause:** encryption strong at the edge and in the database but not on every internal hop; backup and log keys not separated from the account's default keys.
- **Mitigation:** TLS to the containers, own CMKs for backups and logs, TLS-only targets, live verification at go-live.
- Likelihood, impact and residual: set in MO-031.
