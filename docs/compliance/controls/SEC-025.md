## Requirement
Every production change (code, configuration, infrastructure) is requested, approved, tested, deployable, reversible and recorded. For any production change of the last quarter, the who/what/when/approval chain is retrievable in minutes (gate items A1, A8).

## How MoDocument meets it today

The process is built and documented. It is **not operating** as designed: GitHub Actions has run no job since 2026-10-16, and recent merges had no second-person review.

## Questionnaire answer (final)
Changes to MoDocument follow a written change procedure (normal, standard, security-configuration and emergency changes). Code changes go through pull requests with a security and privacy checklist and automated CI (build, unit and PostgreSQL tests, secret scanning, SAST, dependency checks). Releases are tagged versions built once, scanned, deployed to staging, smoke-tested and promoted to production only after approval by two reviewers who did not cut the release; rollback is automatic on a failed deployment and manual by version through the same pipeline; database migrations are expand-only. In-app security settings require a second approver, and every configuration change is recorded with old and new values in an append-only audit trail that administrators can browse and export. MoDocument is pre-production: no production change has happened yet. Our own review on 19 Oct 2026 found that the CI service has not run since 16 Oct and that recent merges lacked a second reviewer; both are being corrected before go-live (evidence SEC-025-E01).
