## Requirement
Operate RBAC from a versioned role–permission matrix that the server enforces. Every API route must map to a named permission.

## How MoDocument meets it today
The workbook entry of 2 October ("not implemented, one shared account") is out of date. The repository holds a complete, tested RBAC system:

- **Model.** Users have roles, and roles grant permissions. There are 6 roles (`src/main/java/com/modocument/domain/model/Role.java`) and 41 `resource:action` permissions (`src/main/java/com/modocument/domain/model/Permission.java`).
- **Matrix as data, under version control.** The grants live in `src/main/java/com/modocument/application/security/RolePermissions.java`. They are rendered into `docs/security/role-permission-matrix.csv`, and the build fails if the two differ (`src/test/java/com/modocument/application/security/RolePermissionMatrixTest.java`). Any change to a grant is therefore a reviewed pull request.
- **One central authorisation point.**
  - Each handler carries `@RequiresPermission` (`src/main/java/com/modocument/api/security/RequiresPermission.java`), a composed `@PreAuthorize`.
  - That annotation is evaluated by one bean, `PermissionChecker` (`src/main/java/com/modocument/api/security/PermissionChecker.java`).
  - The bean denies by default when no usable role is present. It adds the platform-bank guard and API-client scope narrowing, and it blocks everything except self-service while a temporary password is in use.
- **Route coverage test.** `src/test/java/com/modocument/api/security/RoutePermissionCoverageTest.java` fails the build when a handler has no permission, or has two. It also fails when a permission guards no route. The inventory for this pack has 245 routes: 238 guarded and 7 on the public allowlist (login, refresh, MFA verify, SSO providers, synthetic probe, OAuth token, agent enrolment). See `docs/compliance/evidence/A4-route-permission-inventory.md`.
- **Data scoping below the permission layer.**
  - Every tenant table is under PostgreSQL row-level security. The application connects as the `NOBYPASSRLS` role `modocument_app` (`src/main/resources/db/migration/V12__app_role_grants.sql`, `src/main/resources/db/migration/V13__rls_policies.sql`).
  - Inside a bank, jobs, documents and private templates are scoped to their owner (`src/main/java/com/modocument/application/usecase/TemplateOwnership.java`).
- **Individual accounts.** Each person has their own login with MFA (forced for ADMIN and PLATFORM_ADMIN), so roles apply per person. Whether the team's shared pre-production account has been retired is `TO CONFIRM (organisational)`.
- **Documents.** The full matrix by business capability is in `docs/compliance/mo-018-rbac-role-permission-matrix.md`. The live verification is in `docs/compliance/mo-019-role-based-access-system-report.md`.

## Questionnaire answer (final)
MoDocument uses role-based access control enforced on the server. Each user holds exactly one of four bank roles: Administrator, Approver, Read-write or Read-only. MO Intelligence staff use a separate platform role that cannot see any bank's data. Machine integrations use a client role limited to the scopes granted to each client. The 41 permissions take the form "resource:action". Every API route requires exactly one permission, checked in a single authorisation component. An automated test fails the build if any route is left unmapped. The role–permission matrix is kept under version control as code, and a second test fails the build if the published matrix and the code differ. Below the permission layer, database row-level security confines each user to their own bank. We verified enforcement by calling each role's routes on a running system. Evidence SEC-011-E01.

## Test SEC-011-T01
- **Procedure:**
  1. Run `RoutePermissionCoverageTest` and `RolePermissionMatrixTest`.
  2. Generate the route inventory.
  3. Start the production-profile stack (`e2e/run-local.sh`) and call a representative route for every permission as each of the 6 roles, a second bank's ADMIN and an anonymous caller. Compare the result with the CSV.
- **Expected result:** every API route maps to a named permission, and every role is allowed or denied exactly as the matrix says.
- **Actual result:**
  - Both tests passed (`docs/compliance/evidence/A4-test-runs.md`).
  - 238 of 245 routes carry a permission; the other 7 are the public allowlist.
  - Live probe: 352 of 352 role × route calls matched the matrix (126 allowed, 182 denied with 403, 44 anonymous refused with 401) (`docs/compliance/evidence/A4-rbac-probe.md`).
- **Result:** Pass · tester: Agent A4 (automated re-performance); human sign-off required · date: 2026-10-19

## Risk R-SEC-011
- **Risk:** an unmapped endpoint defaults to open, or privilege creep goes unnoticed.
- **Cause:** a route without an explicit permission mapping.
- **Mitigation:** the coverage test makes an unmapped route a build failure. The matrix is code, and every change to it is a reviewed diff.

Likelihood, impact and residual are set in MO-031.
