## Requirement
Ship a role catalogue that mirrors real banking job functions and that a client can customise. The system must reject a conflicting combination of roles for one user.

## How MoDocument meets it today
The workbook's gap ("Approver role not yet built; SoD conflict table not documented") is closed in the repository.

- **Approver role built.** `APPROVER` is in `src/main/java/com/modocument/domain/model/Role.java`. It holds the read permissions plus `change:approve`, `doc:release` and `audit:read`, and no write permission (`src/main/java/com/modocument/application/security/RolePermissions.java`).
- **Role catalogue with job functions.** `docs/security/role-catalogue-and-sod.md` §1 maps the roles to bank functions:

  | Role | Bank function |
  |---|---|
  | `ADMIN` | Application owner / IT administration |
  | `APPROVER` | Supervisor / four-eyes checker |
  | `READ_WRITE` | Operations / report author (maker) |
  | `READ_ONLY` | Auditor / controller / second-line risk |

  It also covers the two non-bank roles, `PLATFORM_ADMIN` and `API_CLIENT`. This pack updated the catalogue to match the code on `audit:read` and `integration:run`. The checklist's business roles are mapped in `docs/compliance/mo-018-rbac-role-permission-matrix.md` §2.
- **SoD conflict table as data.** `src/main/java/com/modocument/application/security/SodPolicy.java` holds the table, rendered in `docs/security/role-catalogue-and-sod.md` §2: maker ≠ checker for every pending change, and author/submitter ≠ releaser for documents.
- **Conflicting role pairs cannot be assigned.** A user holds exactly one role, in a single enum column. `SodPolicyTest.aUserHoldsExactlyOneRole` asserts this, so there is no role set in which two roles could be combined. A role change replaces the role, and the change itself is maker/checker.
- **Roles are bound to the kind of bank.** A customer bank can hand out only the four bank roles. `PLATFORM_ADMIN` is refused there by `src/main/java/com/modocument/application/security/RoleAssignmentPolicy.java` and by the V210 database trigger (`src/main/resources/db/migration/V210__ws21_platform_bank.sql`).
- **Client customisation.** A bank models its finer job functions in its own identity provider and maps them onto the four roles through the OIDC `role-claim` / `default-role` settings (`docs/security/identity-providers.md`). Banks cannot define new MoDocument roles. This is a design choice that keeps one enforcement vocabulary.

## Questionnaire answer (final)
MoDocument's roles follow bank job functions:

- **Administrator** — application owner and user administration.
- **Approver** — supervisor and four-eyes checker. Approves changes and releases reports, but cannot author them.
- **Read-write** — operations staff who prepare data and reports.
- **Read-only** — auditors and controllers.

A bank maps its own job functions onto these roles through its identity provider. Each user holds exactly one role, so conflicting role combinations cannot be assigned at all. The conflicting duties within a role (maker and checker of the same change, author and releaser of the same report) are separated per object and refused by the system. The role catalogue and the conflict table are maintained alongside the code. Evidence SEC-012-E01.

## Test SEC-012-T01
- **Procedure:**
  1. Run `SodPolicyTest` and `RoleAssignmentPolicyTest`.
  2. On the live stack, try to give a customer-bank user the `PLATFORM_ADMIN` role.
  3. Check that the data model has no way to hold a second role.
- **Expected result:** assigning a conflicting role pair to one user is rejected by the system.
- **Actual result:**
  - Both test classes passed, with 12 tests in total (`docs/compliance/evidence/A4-test-runs.md`).
  - The live request to create a `PLATFORM_ADMIN` user in a customer bank returned 400, "Unknown role 'PLATFORM_ADMIN'; use ADMIN, APPROVER, READ_WRITE or READ_ONLY." (`docs/compliance/evidence/A4-rbac-probe.md`).
  - A pair of roles cannot be expressed at all: there is one role column per user.
- **Result:** Pass · tester: Agent A4 (automated re-performance); human sign-off required · date: 2026-10-19

## Gap and remediation
- **Gap.** None in the product. The catalogue's annual review has not yet been held.
- **Gap type:** Org.
- **Action:** review the role catalogue once a year and with each release that changes `RolePermissions`.
- **Owner:** Software Engineering — Bhavish Nobeen.
- **Target date:** 2026-10-21 (first review, workbook date).
- **Roadmap phase:** Day 30.

## Risk R-SEC-012
- **Risk:** tellers receive supervisor rights because no finer role exists.
- **Cause:** a catalogue with only user and admin roles.
- **Mitigation:** four bank roles, with checker rights separated from authoring rights, and IdP mapping for finer functions.

Likelihood, impact and residual are set in MO-031.
