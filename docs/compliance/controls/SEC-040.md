## Requirement
Deliver both readings of "security matrix": the access-control matrix (who
can do what) and the threat–control matrix (preventive, detective and
corrective controls per threat). Acceptance: every threat row has at least
one detective control with a tested alert.

## How MoDocument meets it today
- **Access-control matrix:** `docs/security/role-permission-matrix.csv` — 6
  roles × 41 permissions. It is not hand-written any more:
  `RolePermissionMatrixTest` renders the matrix from the code
  (`src/main/java/com/modocument/application/security/RolePermissions.java`)
  and fails the build if the committed file differs by one byte, so every
  release carries the matrix the code enforces (pass, 2026-10-19). Role
  descriptions and SoD conflicts: `docs/security/role-catalogue-and-sod.md`;
  the full RBAC write-up is MO-018 in this pack.
- **Threat–control matrix:** `docs/security/threat-control-matrix.md`,
  version 1.1 draft of 2026-10-19 with a version table: 12 threats ×
  preventive / detective controls, each with its test or Terraform path and
  an honesty flag (✅ tested, 🏗️ unapplied IaC, ⏳ pending).
- **Acceptance check added:** a per-threat table naming the alert rule and
  the test that trips it. Result: 4 of 12 threats have a detective control
  with a tested alert (brute force, cross-tenant access, insider export; web
  and API abuse partly); 2 have alert rules without a trip test (token theft,
  AI abuse); 6 have no alerting detective control (ransomware, supply chain,
  log leak, spoofed identity, malicious upload, web extraction).
- **Masked identifiers:** the workbook draft says "no role can view unmasked
  identifiers". The masking matrix is per channel × role
  (`docs/security/masking-matrix.md`, `MaskingGateC2Test`); whether any role
  has an unmasked view in some channel is answered there, not restated here.

## Questionnaire answer (final)
We maintain two security matrices as versioned documents. The access-control
matrix lists six roles against 41 permissions; it is generated from the
application's authorisation code and checked on every build, so the document
always matches what the system enforces. The threat–control matrix lists
twelve threats with their preventive and detective controls and the test or
infrastructure code that proves each one, and is reviewed monthly. Four of
the twelve threats already have a detective control with an automatically
tested alert; tests for the remaining alert rules and decisions on the
threats without an alert are scheduled for November 2026. Personal
identifiers are masked per role and per output channel. Evidence SEC-040-E01.

## Test SEC-040-T01
- **Procedure:** for each threat row, find a detective control whose alert
  rule is tripped and asserted by a passing test; re-run those tests.
- **Expected result:** every threat row has at least one detective control
  with a tested alert.
- **Actual result:** 4 of 12 rows meet it, one of them partly (`AlertingGateD1Test`,
  `AccessDeniedBurstAlertTest`, `ExportCapGateD2Test`, `PlatformChangeAlertTest`
  — all pass 2026-10-19; the web/API row only partly). Token theft and AI
  abuse have rules pinned as configuration only. Ransomware, supply chain,
  log leak, spoofed identity, malicious upload and web extraction have no
  alerting detective control.
- **Result:** Partial · tester: Agent A5 (automated re-performance; human
  sign-off required) · date: 2026-10-19.
