# SEC-015 — All privileged session activity logged

| Workbook | Area | Priority | Status (repo-verified) | Evidence ID | Test ID | Risk ID |
|---|---|---|---|---|---|---|

## Requirement
Every privileged action, in the application and on the infrastructure, is
attributable, recorded and tamper-evident. Acceptance: for a test admin
session, the full command/action sequence can be rebuilt from logs the admin
cannot modify.

## How MoDocument meets it today

**In the application (in code, tested):**

- Every security-relevant action writes one `AuditEvent` row: when
  (`OccurredAt`), bank, actor id, e-mail and role, session id (`SessionJti`),
  request id, IP, action, target entity, old and new values, outcome
  (`src/main/java/com/modocument/domain/entity/AuditEvent.java`). The row is
  written in the same transaction as the change
  (`src/main/java/com/modocument/infrastructure/audit/JpaAuditRecorder.java`).
- **The admin cannot modify it:** UPDATE, DELETE and TRUNCATE are revoked
  from the runtime role and blocked by triggers even for the schema owner
  (`src/main/resources/db/migration/V14__audit_event.sql`, proven by
  `AuditAppendOnlyPgIT` — PostgreSQL test, passed on the scratch PostgreSQL 16 on 2026-10-19, see `docs/compliance/evidence/A7-runs.md`). Rows are
  bank-scoped by RLS (`AuditLogRlsPgIT`).
- **Privileged actions covered:** user creation, role change, MFA and
  password resets, user-list export (`UserAdminIntegrationTest`);
  maker/checker changes and self-approval attempts
  (`MakerCheckerIntegrationTest`); security and platform settings, bank
  lifecycle and egress approvals (`PlatformChangeAlertTest`); DSR exports and
  erasures; reading or exporting the audit log is itself audited
  (`AuditViewAuditQaTest`). Catalogue: `docs/security/audit-events.md`.
- **Review:** audit viewer for `ADMIN` and `APPROVER` (`AUDIT_READ`):
  `GET /api/admin/audit`, CSV export, page
  `frontend/src/pages/AuditLogPage.jsx`
  (`src/main/java/com/modocument/api/controller/AuditLogController.java`); the
  same rows go to the bank's SIEM (SEC-031).
- **Alerts on privileged use:** `admin-login`, `privileged-change`,
  `admin-action-burst`, `security-setting-changed`, `platform-change`,
  `announcement-change` (`src/main/resources/application.yml`).

**On the infrastructure (Terraform written and validated, not applied):**

- CloudTrail, multi-region, log-file validation on, written to the
  Object-Lock bucket (`infra/terraform/modules/security-monitoring/main.tf`).
  Until the separate lock account exists the bucket is in the same account
  (still WORM).
- No SSH: ECS nodes have no key pair and use Session Manager
  (`infra/terraform/modules/ecs-app/main.tf`); the Session Manager document
  records every session to the locked bucket and CloudWatch
  (`aws_ssm_document.session_preferences` in
  `infra/terraform/modules/security-monitoring/main.tf`).
- Database: the RDS parameter group logs DDL, connections and disconnections
  (`log_statement = ddl`, `infra/terraform/modules/rds/main.tf`). **pgAudit is
  not configured**, so reads and DML by a person at a database console are
  not recorded.
- Azure Activity Log (named in the owner statement): nothing about Azure is
  in this repository.

## Questionnaire answer (final)
Every privileged action in the application is written to an append-only
audit trail with who, when, from which address and session, what was changed
and the before and after values. The database itself refuses updates and
deletes on that table, including by the database owner, and every privileged
action is also streamed to the bank's SIEM; reading the audit log is itself
audited. Administrator sign-ins and privileged changes raise security alerts.
For the AWS infrastructure we use no SSH: server access goes through AWS
Session Manager with session recording to write-once storage, and CloudTrail
records all control-plane activity with log-file validation. These
infrastructure controls are defined as code and are switched on with our
first production deployment; database statement-level audit logging (pgAudit)
is planned for 13 November 2026. Evidence SEC-015-E01.

## Test SEC-015-T01
- **Procedure:** in-app part: re-run the tests that perform admin actions and
  assert their audit rows (user administration, maker/checker, settings,
  audit viewing); check that each row carries actor, session, IP, request id
  and old/new values; check the append-only mechanism in the migration.
  Infrastructure part: inspect the Terraform for CloudTrail, Session Manager
  recording and database audit.
- **Expected result:** for a test admin session, the full command/action
  sequence is reconstructable from logs the admin cannot modify.
- **Actual result:** in-app sequence reconstructable: the listed tests pass
  (52 + 92 tests in the two runs of 2026-10-19, 0 failures) and the audit rows
  carry session id and request id, so one session's actions can be listed in
  order. Append-only is enforced by `V14__audit_event.sql` (PgIT proof not
  re-run here). Infrastructure sessions: not testable — nothing is deployed;
  database console statements other than DDL would not be recorded (no
  pgAudit).
- **Result:** Partial · tester: Agent A5 (automated re-performance; human
  sign-off required) · date: 2026-10-19.

## Risk R-SEC-015
Admin abuse or error cannot be rebuilt and investigations stall. Cause:
infrastructure access is not yet routed through a recording path and
database statements are not audited. Mitigation: append-only in-app audit
today; Session Manager recording, CloudTrail and pgAudit at deployment.
Likelihood, impact and residual are set in MO-031.
