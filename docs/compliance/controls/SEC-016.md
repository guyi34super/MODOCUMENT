## Requirement
Reporting is itself permission-scoped. A dedicated dashboard shows privileged activity. The same report must return different scopes for different roles.

## How MoDocument meets it today
The workbook says "not built". In fact every reporting surface is a normal API route behind the same `@RequiresPermission` check and the same tenant scoping. There is no separate reporting path to the database.

| Report / dashboard | Route | Permission (roles) | Scope |
|---|---|---|---|
| Bank admin dashboard | `GET /api/admin/dashboard` | `metrics:read` (ADMIN) | Caller's bank only (`src/test/java/com/modocument/api/AdminDashboardIsolationTest.java`, `src/test/java/com/modocument/pgit/AdminDashboardIsolationPgIT.java`) |
| User dashboard summary | `GET /api/dashboard/summary` | `ingestion:read` (bank roles) | "The caller's dashboard" (`src/main/java/com/modocument/api/controller/DashboardController.java`) |
| Audit trail browse + CSV export | `GET /api/admin/audit`, `GET /api/admin/audit/export` | `audit:read` (ADMIN, APPROVER; PLATFORM_ADMIN for the platform bank) | Caller's bank (`src/test/java/com/modocument/pgit/AuditLogRlsPgIT.java`) |
| Alerts (incl. `privileged-change`, `platform-change`, `admin-login`) | `GET /api/admin/alerts` | `user:admin` (ADMIN) | Caller's bank |
| Records search (validated data) | `GET /api/doccreation/records` | `ingestion:read` | Own jobs and bank-shared templates; **masked by role** |
| Data exports | `GET /api/ingestion/jobs/{id}/export/file` | `export:run` (ADMIN, READ_WRITE) | Own job; **masked for every role** |
| Platform overview | `GET /api/platform/overview` | `platform:read` (PLATFORM_ADMIN) | Counts only, no row content (`docs/platform/platform-owner.md`) |

Column-level control comes from `MaskingPolicy` (`src/main/java/com/modocument/application/privacy/MaskingPolicy.java`, `docs/security/masking-matrix.md`). Reports and exports mask NIC, account, e-mail, phone and name for every role. Screens mask them for `READ_ONLY`.

**Privileged activity.** Privileged actions raise the `privileged-change` and `platform-change` alerts (`src/main/resources/application.yml`, `docs/security/alerting-and-export-caps.md`). They can be filtered in the audit-log screen (`frontend/src/App.jsx` route `/admin/audit`). There is no single dedicated "privileged activity" dashboard page. The monthly review in `docs/compliance/policies/privileged-access-and-break-glass.md` uses the audit filters instead.

## Questionnaire answer (final)
Reports and dashboards in MoDocument go through the same permission checks and bank isolation as the rest of the application. There is no separate reporting path to the database.

- Each user sees only their own bank's data, and only the reports their role allows: the admin dashboard and alerts for administrators, the audit trail for administrators and approvers.
- Personal data in reports and exports is masked for every role.
- On screens, read-only users see personal data masked, while preparers and approvers see it in full.
- We tested the same records report with five roles across two banks. It returned full values, masked values or no access, as the role required.
- Privileged actions raise immediate alerts and can be filtered in the audit trail.
- A dedicated privileged-activity dashboard page is planned.

## Test SEC-016-T01
- **Procedure:**
  1. On the live stack, a READ_WRITE user runs synthetic personal data (name, NIC, phone) to VALIDATED on a bank-shared template.
  2. The same records report (`GET /api/doccreation/records?templateId=…`) is requested as the owner, as APPROVER, ADMIN and READ_ONLY colleagues, as the ADMIN of bank B and as PLATFORM_ADMIN.
  3. The owner exports the job as a file.
  4. In addition, run the dashboard isolation tests.
- **Expected result:** the same report ID returns different scopes for different roles.
- **Actual result:**
  - Owner, APPROVER and ADMIN: 200 with the raw NIC.
  - READ_ONLY: 200 with `********`.
  - Bank B ADMIN: 404. PLATFORM_ADMIN: 403.
  - Export file: 200, and the raw NIC is absent.
  - Dashboard tests: 3 H2 tests and 2 PostgreSQL tests passed.
- **Result:** Pass · tester: Agent A4 (automated re-performance); human sign-off required · date: 2026-10-19

## Gap and remediation
- **Gap:**
  - No dedicated privileged-activity dashboard page; the audit filters and alerts are used instead.
  - The `admin-login` alert covers `ADMIN` but not `PLATFORM_ADMIN` sign-ins (`actor-roles: [ADMIN]` in `src/main/resources/application.yml`; MO-019 exception X-05).
  - The raw records view for colleagues needs the DPO's decision (MO-019 exception X-03).
- **Gap type:** Build.
- **Action:**
  - Add a privileged-activity view to the admin and platform dashboards, based on the audit actions named in the monthly review procedure.
  - Add `PLATFORM_ADMIN` to the `admin-login` rule.
- **Owner:** Software Engineering — Bhavish Nobeen.
- **Target date:** 2026-11-30 (proposed). The workbook date of 2026-10-21 will not be met for the dashboard page.
- **Roadmap phase:** Day 60.

## Risk R-SEC-016
- **Risk:** a low-privilege user exports through reports what the UI would deny.
- **Cause:** a report engine that queries the database outside the authorisation layer.
- **Mitigation:** there is no such engine. Every report is an authorised, tenant-scoped API route. Exports are masked and limited to ADMIN and READ_WRITE.

Likelihood, impact and residual are set in MO-031.
