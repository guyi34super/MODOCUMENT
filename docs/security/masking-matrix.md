# PII masking matrix (ws12 — gate C2, PRIV-004 / PRIV-005)

Gate C2: **NIC and account numbers are masked for every role in screens,
reports and exports** — a sample of each channel shows only masked values.

Three pieces implement it, all under `application/privacy`:

* **Classification (PRIV-004)** — every template field carries a `PiiKind`
  (`TemplateFields.PiiKind`, V100): `NIC`, `ACCOUNT_NUMBER`, `EMAIL`,
  `PHONE`, `NAME` or `NONE`. The template owner tags fields explicitly in
  the template editor; an untagged field is classified once by
  `PiiClassifier` (field name → rule types → unanimous value shapes via the
  shared `PiiPatterns`) and the result is persisted, so it is visible and
  correctable. An explicit tag — including `NONE` — always wins and is
  never re-inferred.
* **Policy (PRIV-005)** — `MaskingPolicy` is the channel × role matrix
  below, as data. `PiiMaskingService` applies it at each channel's choke
  point.
* **Engine** — `Masker` holds the per-kind rules (idempotent and
  null-safe, so re-masking a masked value is a no-op).

## Per-kind masking rules (`Masker`)

| PiiKind        | rule                              | example                           |
|----------------|-----------------------------------|-----------------------------------|
| NIC            | fully masked, fixed width         | `M090976290148E` → `********`     |
| ACCOUNT_NUMBER | last 4 kept                       | `00445566778899` → `****8899`     |
| EMAIL          | first char + domain kept          | `jane@acme.mu` → `j***@acme.mu`   |
| PHONE          | last 2 kept                       | `+230 5712 3456` → `****56`       |
| NAME           | first letter kept                 | `Anna Smith` → `A***`             |
| NONE / untagged-and-classified-NONE | untouched    |                                   |

## Channels and their choke points

* **EXPORT** — masked for every role. Applied in
  `IngestionExportController.exportableTable`, so all three artifacts carry
  the same masked bytes: the file download (csv/json/xlsx/tsv/xml via
  `FileExportService`), the per-owner archive copy under
  `wwwroot/exports/u{owner}/` (written from the same byte array), and the
  database export (`DatabaseExportService` inserts the same masked
  `TableData`). Note `export:run` itself is already restricted to
  ADMIN/READ_WRITE by the role matrix — masking applies on top, to every
  role that can export at all.
* **REPORT** — masked for every role. Generated documents
  (`DocInstanceUseCase.generate`, both the AI composer and the
  deterministic assembler) contain only user-typed content blocks — no job
  data is injected into that path — so the PII value *shapes* in paragraph
  text and image captions (NIC, bare account digit runs, emails) are
  masked by `Masker.maskShapes` at render time, on detached copies. The
  stored blocks keep the user's raw text (the builder screen is
  SCREEN_WORKING; DSR search/erase still sees it), and the masked text is
  also what the AI composer's prompt receives.
* **SCREEN_READONLY** — masked for every role. A READ_ONLY caller reading
  `GET /api/ingestion/jobs` or `GET /api/ingestion/jobs/{id}` gets masked
  parsed/mapped/validation payloads. Jobs are owner-scoped, so in practice
  this is an owner whose role was downgraded to READ_ONLY viewing their old
  data — cross-user reads 404 before masking is ever consulted. Mapped
  rows and validation results mask by the template-field classification;
  the parsed table's raw source columns mask by header-plus-shape
  inference (not persisted — source columns are not template fields).
  Validation error messages additionally go through shape masking, because
  rule messages can quote the failing value.
* **SCREEN_WORKING** — **raw by default, documented exception.** The
  owner's editing wizard (mapping review, cell fixes, chat edit) exists to
  correct the true values; masking it would break the product's core
  workflow. PRE-RELEASE justification: jobs are strictly owner-scoped and
  the role holding this channel (`ingestion:write`) uploaded the very file
  it is editing — the channel discloses nothing the caller did not already
  possess. Deployments that want it anyway set
  `modocument.privacy.masking.screen-working=true`, which force-masks the
  job read routes for writing roles too. The write-route echoes
  (PUT rows/mapping responses) return what the caller just submitted.
* **DSR** — never masked, by design (PRIV-016 / ws14): the data-subject
  export's purpose is complete disclosure to the subject. It is
  `user:admin`-gated, audited (`DSR_EXPORTED`), and builds its own ZIP in
  `DataSubjectUseCase` — it does not route through `FileExportService`
  serialization or the masking service, and the C2 gate test pins that it
  still returns raw values.

## Known non-channels (out of ws12 scope, tracked)

* `ImportDetails.RawJson` / import history payloads repeat parsed-table
  checkpoints to their owner (`import:read` is owner-scoped); they render
  on the owner's working screens only.
* AI prompts are not a human channel: they are tokenized by
  `PiiTokenizer` (which shares `PiiPatterns` and now recognizes `nic`
  field names and letter-prefixed NIC shapes) before leaving the backend.
* Logs and persisted error text are ws13's `LogSafe.scrub` /
  `«redacted»` pipeline, built on the same `PiiPatterns`.
