# OWASP API Security Top 10 (2023): controls and evidence

Gate **E2**: the API is authenticated, permission-checked, rate-limited, TLS-only and documented
in OpenAPI. Controls: **SEC-006** (API catalogue), **SEC-007** (defence in depth on every call),
**SEC-008** (capacity; scenarios are prepared, execution is gate E7).

Each row names the implemented control and the test that proves it. Every test runs in
`mvn -B verify`, except `*PgIT` tests, which run in the `-Ppostgres-it` CI job against real
PostgreSQL. The **Gaps** column lists what is not covered.

| # | Risk | Implemented controls | Evidence (tests) | Gaps |
|---|---|---|---|---|
| API1 | Broken Object Level Authorization | Owner-scoped queries (`*ByOwner`). Another user's ids answer **404**, never data. Bank tenancy is enforced in the app by `TenantContext` (bank_id from the JWT) and in the database by PostgreSQL row-level security on every `BankId` table. Upload ownership (V20): a stored file name is usable only by its uploader. Template and document ownership gates. | `CrossUserAccessTest`, `ExtractionCrossUserAccessTest`, `DocCreationOwnershipIntegrationTest`, `UploadOwnershipEnforcementTest`, `TenantIsolationGatePgIT` (C1: cross-bank calls refused over HTTP and at SQL level), `RlsPolicyCoveragePgIT` | Cross-bank refusal is proven only in the PostgreSQL job, because H2 has no RLS. The H2 suite covers app-level scoping only. |
| API2 | Broken Authentication | 15-minute HS256 access tokens. Server-side revocation: jti denylist, `TokenVersion` bump on password or role change. Rotating refresh cookie (`httpOnly`, `Secure`, `SameSite=Strict`, fixed family expiry, reuse kills the family). Argon2id password hashes. Lockout after repeated failures. Password policy. TOTP MFA, enforced for ADMIN. Throttles: login and refresh per IP and per email (`AuthRateLimiter`); MFA verify per IP and per user (`MfaRateLimiter`). **New in workstream 17:** per-user buckets on the authenticated credential checks: password change 5/h; MFA activate and disable 10/h. Before this, a stolen access token could brute-force the TOTP code that disables MFA. | `AuthFlowIntegrationTest`, `AccountLockoutIntegrationTest`, `MfaFlowIntegrationTest`, `RevocationValidatorTest`, `JwtServiceTest`, `PasswordPolicyTest`, `LoginLockoutPolicyTest`, `ApiRateLimitIntegrationTest` (`password-change`, `mfa-code`, shared-bucket case) | All instances share one HS256 secret: there is no asymmetric signing and no key-rotation tooling. | API4 | Unrestricted Resource Consumption | **One per-user rate-limit interceptor** (`ApiRateLimitInterceptor`) on every expensive endpoint (see the bucket table below). (3) Authenticated reads have no global per-IP or per-user request cap; that is left to the edge or WAF. | API6 | Unrestricted Access to Sensitive Business Flows | Maker-checker on user-security changes and, optionally, template changes (B7). ## Rate-limit buckets (`modocument.ratelimit.*`, workstream 17)

There is one fixed window for every bucket, 1 hour by default (`MODOCUMENT_RATELIMIT_WINDOW_MILLIS`).
Limits are counted **per user**, the JWT subject. A bucket is chosen from the handler's
**matched route pattern and method**, not from the raw URI, so casing, path variables and matrix
parameters cannot move a call into a different bucket. HEAD is counted as GET. Over the limit:
**429**, with a `Retry-After` header giving the seconds left in the window and an `{"error": ...}`
body.

| Bucket | Default / user / h | Env override | Routes |
|---|---|---|---|
| `uploads` | 20 | `MODOCUMENT_RATELIMIT_UPLOADS` | `POST /api/fileupload/upload`, `POST /api/doccreation/instances/{id}/assets`, `POST /api/doccreation/blueprints` |
| `ingestion` | 60 | `MODOCUMENT_RATELIMIT_INGESTION` | `POST /api/ingestion/jobs` (multipart and JSON), `POST .../jobs/{id}/resume`, `.../remap`, `.../revalidate` |
| `transform` | 30 | `MODOCUMENT_RATELIMIT_TRANSFORM` | `POST /api/transform/transform` |
| `exports` | 60 | `MODOCUMENT_RATELIMIT_EXPORTS` | `GET /api/ingestion/jobs/{id}/export/file`, `POST .../export/file` (ws18: same export with `{format, reason}` in the body), `POST .../export/database` |
| `doc-generate` | 30 | `MODOCUMENT_RATELIMIT_DOC_GENERATE` | `POST /api/doccreation/instances/{id}/generate` |
| `extraction` | 30 | `MODOCUMENT_RATELIMIT_EXTRACTION` | `POST /api/extraction/jobs` (starts by default), `POST .../jobs/{id}/start`, `POST .../jobs/{id}/bridge` |
| `dsr` | 10 | `MODOCUMENT_RATELIMIT_DSR` | `POST /api/admin/dsr/search`, `.../export`, `.../erase` |
| `password-change` | 5 | `MODOCUMENT_RATELIMIT_PASSWORD_CHANGE` | `PUT /api/auth/password` |
| `mfa-code` | 10 | `MODOCUMENT_RATELIMIT_MFA_CODE` | `POST /api/auth/mfa/activate`, `DELETE /api/auth/mfa` |
| `admin-jobs` | 10 | `MODOCUMENT_RATELIMIT_ADMIN_JOBS` | `POST /api/admin/retention/run`, `POST /api/admin/sod/scan` |
| `admin-security` | 10 | `MODOCUMENT_RATELIMIT_ADMIN_SECURITY` | `POST /api/admin/users/{id}/password-reset`, `.../mfa-reset` |

Other switches: `MODOCUMENT_RATELIMIT_ENABLED` (master switch, default `true`) and
`MODOCUMENT_RATELIMIT_MAX_KEYS` (memory bound).

**Limiters already in place before workstream 17. No endpoint is counted by two limiters for
the same resource:**

| Limiter | Scope | Routes | Overlap decision |
|---|---|---|---|
| `LlmQuotaInterceptor` → `LlmRateLimiter` | per user, 60/h (`modocument.security.rate-limit.llm.*`) | `/api/aifiles/send`, `/api/automapper/generate`, `/api/ingestion/jobs/*/chat-edit`, **+ `/api/extraction/jobs/*/infer-schema`, `/api/extraction/jobs/*/summary` (ws17)** | Not in the bucket table. `transform` also calls the LLM but is counted **only** by its own 30/h bucket, which is tighter. Document generation is counted in `doc-generate` for its rendering cost; when AI composition is on it also draws on the LLM quota inside `AiDocumentComposer`, where running out falls back to the deterministic engine instead of failing. These are two different resources, and counting both is intended. Blueprint upload counts in `uploads`, and its AI section split also draws on the LLM quota inside `AiSectionSplitter`, the same reasoning. |
| `AuthRateLimiter` | per IP 30 and per email 10 per 15 min | `POST /api/auth/login`, `POST /api/auth/refresh` | Anonymous-phase throttle. Not in the bucket table. |
| `MfaRateLimiter` | per user 5/min (the brute-force control); per IP 30/min (flood guard sized for a bank's shared NAT, QA finding OBS-04) | `POST /api/auth/mfa/verify` | Anonymous-phase throttle. The authenticated TOTP checks (activate and disable) are in the `mfa-code` bucket instead. Both limits are platform settings (`ratelimit.mfa.*`); rationale in [../settings/catalogue.md](../settings/catalogue.md#mfa-verify-per-address-qa-finding-obs-04). |
| `SyntheticProbeController` (ws18) | per IP, 60/min (`MODOCUMENT_PROBE_RATE_LIMIT`) | `GET /api/probe/synthetic` (public) | Anonymous by design (an uptime monitor holds no credentials), so it cannot be in the per-user bucket table; its own per-IP limiter is the only one that counts it. |
| — | — | multipart `POST /api/ingestion/jobs` | This is an upload, but it counts only in `ingestion`, never in `uploads` as well. |

**Why ADMIN has the same limits.** These limits contain abuse and resource exhaustion; they do
not ration legitimate work. An admin token is exactly as scriptable as any other, and it is the
most valuable token to steal. An exemption would remove the containment from the account where
it matters most. If a workload genuinely needs more, operations raises that bucket with its
environment variable, which applies to everyone and leaves an auditable configuration change.
`ApiRateLimitIntegrationTest` runs every case as an ADMIN.
